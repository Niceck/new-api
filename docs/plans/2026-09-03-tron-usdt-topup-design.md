# TRON / TRC20-USDT 充值设计

## 目标与约束

为 New API 钱包页增加 TRON 主网 TRC20-USDT 充值。用户输入希望充值的站内金额，服务端读取新鲜的 USDT/CNY 市场报价并在订单创建时锁价，展示唯一、精确到 6 位小数的应付 USDT。用户将该金额转到配置的只读收款地址后，后台监听器只消费已固化的主网 USD₮ 入账事件，在数据库事务中完成去重、订单核对、额度增加和订单完成。

系统永远不持有或请求钱包私钥；TronGrid 和 CoinGecko 凭据仅作为后端环境变量。收款地址可以公开，但主网地址、网络、USD₮ 合约三者必须同时匹配。任何外部 API 响应都按不可信输入校验。无新鲜报价、监听 API 异常、数据库异常时全部 fail closed：不创建错误价格订单、不提前入账、不把未知状态当成功。

CoinGecko Demo/公共端点官方说明多数缓存约 1–5 分钟，因此报价新鲜度上限取 6 分钟，为官方窗口保留传输与秒级时钟余量；超过 6 分钟或超过当前时间 30 秒的报价仍拒绝。订单落库保存 CoinGecko 的实际更新时间和锁定汇率，不能用请求时间伪装数据新鲜度。付费 Pro 的更快缓存不是本部署的前提。

已比较三种识别方式：每用户独立地址需要 HD 钱包和私钥托管，攻击面最大；默认要求用户提交 txid 体验差且容易出现冒领竞态；共享地址配唯一金额不需要签名权限，且能自动识别绝大多数付款。因此选用共享地址 + 全局不复用唯一金额，极端情况由站内工单闭环。

## 数据模型与金额规则

通用 `topups` 表继续承载列表展示和现有支付兼容性；TRON 审计数据使用独立表：

- `tron_topup_orders`：关联 `topups`，保存用户、收款地址、官方 Token 合约、应付 USDT 最小单位整数、锁定的 USDT/CNY 汇率整数、毫秒级报价时间、毫秒级锁价截止时间及精确的待入账 quota。
- `tron_deposits`：每个链上 txid 只登记一次，保存区块时间、来源/目标地址、Token 合约、到账最小单位整数、匹配订单和实际入账 quota。若同一 txid 出现多条目标地址 Transfer 事件，监听器先合并金额再登记。
- `tron_topup_tickets`：保存用户申诉或系统自动升级事件，关联订单/到账、原因、状态和审计备注。
- `tron_scan_checkpoints`：只有整段分页扫描成功后才推进毫秒级 checkpoint；扫描带重叠窗口，重复数据由 txid 唯一约束消化。

金额计算全程用 `shopspring/decimal`，链上金额和汇率落库均为定点整数，不使用 `float64` 做账。理论应付金额先按实际汇率四舍五入到 USDT 最小微单位；默认直接使用该金额，只有发生历史/并发碰撞时才按随机方向从 `+1/-1` 微单位起向外寻找未使用值。总计保留 9,999 个唯一候选，最坏偏移不超过 0.004999 USDT，正常首单只承受不足半个微单位的换算误差；唯一索引保证并发创建也不会碰撞。充值 quota 在创建订单时按当时站点价格、分组倍率、优惠和 `QuotaPerUnit` 固化，超出安全上限直接拒绝。

订单有效期默认 20 分钟，以链上 `block_timestamp <= expires_at_ms` 判断是否按时；即使固化发生在截止后，只要转账进块时间在截止前仍自动入账。默认单笔上限为 ¥2,000，同时按 `common.MaxQuota / QuotaPerUnit` 动态收紧；配置不能放宽代码硬上限，避免 quota 溢出。

## API、监听与幂等入账

用户接口位于现有鉴权路由下：创建/复用有效订单、查询自己的订单状态、提交 txid 申诉。创建接口同时受全局关键请求限流与用户级限流保护；同一用户同一时间只保留一个有效订单。txid 必须是 64 位十六进制，备注有严格长度上限。管理员接口可分页查看工单，并执行“重新验链后处理”或拒绝，不能接受由前端传入的任意额度。

监听器运行在 master 节点后台，每 30 秒扫描一次。它调用 TronGrid 的账户 TRC20 历史接口，固定 `only_confirmed=true`、`only_to=true`、主网 USD₮ 合约、升序时间范围和最多 200 条分页，并保持分页时所有过滤参数不变。增量扫描只推进到“当前时间 - 3 分钟”的保守索引水位并回叠 2 分钟；每小时再做 25 小时宽对账以捕获延迟索引。429/403/5xx 使用有上限的带抖动退避；分页中任一页失败便不推进 checkpoint，下轮安全重放。生产必须配置只读 `TRON-PRO-API-KEY`，但 API key 不具备链上签名权限。

精确且按时到账进入单个数据库事务：锁定 `TopUp` 和 TRON 订单，验证 provider/status/金额/地址/合约/时间，插入唯一 txid 的 deposit，使用固化 quota 更新用户余额，再把两个订单状态置为成功。任何错误都回滚，所以不存在“订单成功但额度没加”的中间态；重复扫描看到成功订单或已消费 txid只做幂等返回。事务后才写展示日志，日志失败不改变资金结果，并产生运维告警。

## 两类工单兜底

第一类是无法自动唯一归属：用户转错金额、超过锁价期、使用旧订单，或监听器看到与有效订单不匹配的到账。系统先保存未匹配 deposit；用户从订单弹窗提交 txid 后创建申诉。txid 是公开信息，不能以“先提交者”证明所有权，因此同一 txid 允许不同用户/订单形成竞争申诉；管理员必须结合交易所出金记录等外部证据选择正确订单。用户只能在订单到期后 24 小时内新增或更正申诉，每个订单最多产生 3 张用户工单；更正会原子关闭旧工单并创建不可变的新 ticket ID，防止管理员审核期间 txid 被静默换绑。处理时再次验证目标地址、官方合约、区块确认和 txid 未被消费；实际金额只允许在订单的 90%–110% 范围，并由服务端按锁定比例计算额度，绝不采用前端或管理员手填额度。最终 deposit 的 txid 唯一约束仍保证只入账一次。

第二类是链上已确认但自动入账不能完成：明确的额度安全边界错误会保留链上 deposit 证据并创建 `credit_failed` 工单；未知 DB/driver/context 错误不推进 checkpoint、也不转人工单，下轮继续自动重放，避免把瞬时故障永久降级成人工处理。工单处理与自动入账共用同一个幂等结算函数，消除两套记账逻辑漂移。

工单状态为 open/resolved/rejected，用户只能查看自己的申诉，管理员能查看完整链上证据与处理结果。拒绝和成功都记录处理人、时间与备注。任何 txid 一旦成功入账，数据库唯一约束阻止它再次绑定其他订单或工单。

## 前端、配置与验收

钱包页新增“USDT (TRON/TRC20)”支付方式。确认后不跳转第三方页面，而是打开专用付款弹窗：网络、官方 Token、收款地址、精确金额、锁定汇率、人民币价值、倒计时、二维码和逐项复制按钮。弹窗明确警告只接受 TRON 主网官方 USD₮，金额必须完全一致，交易所提现手续费不得从到账金额中扣除。前端轮询自己的订单状态；成功后刷新余额，过期或长时间未到账时显示“提交充值申诉”，要求 txid 而不是敏感钱包信息。

TRON 能力与通用易支付方式必须保持跨版本隔离。仅要求用户刷新无法约束部署时已经打开的旧页面；只在易支付入口增加拒绝则仍会让旧页面展示一个不能工作的按钮；由后端继续把 TRON 混入通用 `pay_methods` 也会把它泄漏到订阅购买等只认识易支付的界面。因此采用双层兼容方案：后端只通过 `enable_tron_topup` 宣告能力，并从通用 `pay_methods` 过滤任何 `type=tron`；新版钱包页根据该能力标志生成唯一的 TRON 专用按钮。通用 `/api/user/pay` 再显式拒绝 `tron` 并提示刷新，作为已缓存旧页面的兜底。这样新后端配旧前端时不会展示错误入口，新前端配旧响应时仍只走专用建单逻辑，且任何旧页面都不能创建伪易支付 TRON 订单。

配置项均走环境变量：功能开关、收款地址、TronGrid API key、CoinGecko API key、最大单笔人民币金额、订单有效期和扫描间隔。收款地址启动时必须通过 TRON Base58Check 校验；功能启用时两个只读 API key 都必须非空，compose `${VAR:?}` 与 Go 初始化双重 fail closed。生产 compose 只写公开地址和非敏感参数；密钥留在 root-only `.env`。没有新鲜报价或外部服务不可用时前端展示暂不可用，不提供猜测汇率。关闭新订单时，已有订单查询、申诉、工单列表/拒绝仍保留；需要链上验证的管理员通过操作明确返回暂不可用，绝不无验链补款。

测试按 RED→GREEN 执行：定点换算/唯一尾差、报价过期、分页与 checkpoint、固化过滤、同 tx 多事件合并、准时/超时边界、重复扫描、并发结算、跨 provider 拒绝、金额不符工单、txid 冒领、额度溢出、权限和输入边界；前端覆盖支付路由、弹窗字段、复制/倒计时、状态轮询和申诉入口。最后运行 Go 全量测试、race 定向测试、前端定向测试/typecheck/lint/build、Docker 构建，并在主网用最小金额做一次真实端到端验收后再宣布上线。
